o4-mini:
When you write a long‐running plug-in that drives its own GTK dialog, the single GTK main loop is being held hostage by your C++ processing loop, so none of your widgets ever get a chance to repaint.  The cure is to either:

 1.  let GTK continue to process (a little bit of) its own queue while you’re churning away, or  
 2.  push your heavy work into a background thread (or an idle callback), so that the dialog’s main loop never “freezes.”

Below are two patterns you can choose from.  

—————————————————————  
Pattern 1: Yield to the GTK loop from your processing loop  
—————————————————————

If you must do your work synchronously on the main thread, then inside your long work-loop periodically:

 • call gimp_progress_update() (or gtk_progress_bar_set_fraction())  
 • let pending GTK events run so the dialog and bar actually repaint  

Example (pseudo-C++ with GIMP 3 / GTK4-ish API):

```cpp
#include <gimp.h>
#include <gtk/gtk.h>

void
run_my_heavy_procedure (GtkWidget *dialog,
                        GtkProgressBar *progress_bar)
{
  gdouble total_steps = 1000.0;
  gimp_progress_init ("Crunching pixels…");

  for (gint i = 0; i < (int) total_steps; ++i)
    {
      // 1) do a tiny chunk of your work
      do_one_step_of_the_filter();

      // 2) update the GIMP progress
      gimp_progress_update (i / total_steps);

      // 3) update your GTK ProgressBar if you have one
      gtk_progress_bar_set_fraction (progress_bar, i / total_steps);

      // 4) pump GTK events so they can repaint the bar & dialog
      while (gtk_events_pending ())
        gtk_main_iteration ();
    }

  gimp_progress_end ();
}
```

Key points:

  * gimp_progress_init / gimp_progress_update / gimp_progress_end drive the global GIMP progress bar  
  * gtk_events_pending() / gtk_main_iteration() re-enter GTK’s loop just enough to repaint your widgets  

————————————————————  
Pattern 2: Do the work in an idle callback (or background thread)  
————————————————————

A cleaner approach is to present your “OK” dialog, grab the parameters, then immediately hand off the work to an idle function or separate thread.  The GTK main loop stays free to run the dialog and draw the progress bar; your idle callback gets invoked over and over until the work is done.  Something like:

```cpp
struct MyContext
{
  GtkWidget      *dialog;
  GtkProgressBar *progress_bar;
  int             current_step;
  int             total_steps;
};

// This function is called in the GTK main loop whenever it's idle
static gboolean
my_idle_step (gpointer data)
{
  MyContext *ctx = static_cast<MyContext*>(data);

  if (ctx->current_step >= ctx->total_steps)
    {
      // all done!
      gimp_progress_end ();
      gtk_widget_destroy (ctx->dialog);
      delete ctx;
      return G_SOURCE_REMOVE;  // stop calling me
    }

  // do a bit of work
  do_one_step_of_the_filter();

  // update progress
  gdouble fraction = (gdouble)ctx->current_step / ctx->total_steps;
  gimp_progress_update (fraction);
  gtk_progress_bar_set_fraction (ctx->progress_bar, fraction);
  ctx->current_step += 1;

  // return G_SOURCE_CONTINUE so this is called again
  return G_SOURCE_CONTINUE;
}

void
on_ok_button_clicked (GtkButton *button, gpointer user_data)
{
  // 1) read params from your dialog
  // 2) create context
  MyContext *ctx = new MyContext();
  ctx->dialog       = /* your dialog widget */;
  ctx->progress_bar = /* pointer to your GtkProgressBar */;
  ctx->current_step = 0;
  ctx->total_steps  = 1000;

  // 3) init GIMP progress
  gimp_progress_init ("Crunching…");

  // 4) schedule the idle handler
  g_idle_add (my_idle_step, ctx);

  // 5) disable the OK button so they can't re-submit
  gtk_widget_set_sensitive (GTK_WIDGET (button), FALSE);
}
```

Why this is nicer:

 • You never block GTK’s main loop  
 • Your idle callback runs in small quanta, updating both GIMP’s global progress bar and your local progress bar  
 • When you return G_SOURCE_REMOVE, GTK destroys your dialog and returns control to GIMP  

Either way, the core trick is “don’t let your filter loop monopolize the single GTK thread.”  Either pump the loop yourself (gtk_events_pending/gtk_main_iteration) or hand off work to an idle source (or background thread) so GTK can keep drawing your progress bar.
