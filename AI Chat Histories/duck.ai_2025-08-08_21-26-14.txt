## 🚀 What “#pragma clang loop vectorize(enable)” Does

<b>“#pragma clang loop vectorize(enable)”</b> is a directive that tells the Clang optimizer to <b>actively attempt to vectorize</b> the immediately following loop, even if its default heuristics might skip it. This can expose additional opportunities to transform scalar loop iterations into SIMD (Single Instruction, Multiple Data) operations, improving throughput on vector‐capable CPUs.

<hr>

## 🔍 How It Works Internally

After you annotate a loop with this pragma, Clang’s front end attaches metadata to the loop in the LLVM intermediate representation (IR). During the optimization pipeline:

1. The <b>Loop Vectorizer</b> pass recognizes the metadata hint.  
2. It prioritizes the loop for vectorization, overriding cost-model decisions that might have deemed it unprofitable.  
3. The pass attempts to restructure the loop into a vector form—batching multiple iterations into wide registers (e.g., SSE/AVX).  
4. If successful, the backend generates SIMD instructions; if not (due to dependencies, alignment issues, or unsupported operations), it falls back to a scalar version rather than issuing an error.

<hr>

## 🛠️ Usage and Best Practices

### When to Use  
- Loops with <b>simple, independent operations</b> per iteration (e.g., element-wise array math).  
- Hot paths where profiling shows missed vectorization.  
- Situations where you know alignment, bounds, and absence of data dependencies.

### How to Apply  
```cpp
#pragma clang loop vectorize(enable)
for (int i = 0; i < N; ++i) {
    A[i] = B[i] * scalar + C[i];
}
```

### Interaction with Other Pragmas  
- You can combine it with `unroll(enable)` to both vectorize and unroll:  
  ```cpp
  #pragma clang loop vectorize(enable) unroll(enable)
  for (…) { … }
  ```  
- You may also disable vectorization selectively using `vectorize(disable)` on loops that inadvertently degrade performance when vectorized.

<hr>

## ⚠️ Caveats and Tips

- **Alignment:** Ensure data arrays are suitably aligned (e.g., `alignas(32)`) to avoid unaligned‐load penalties or missed vectorization.  
- **Dependencies:** The pragma won’t override true data hazards; loops with cross-iteration dependencies still won’t vectorize.  
- **Verification:** Always check compiler reports with `-Rpass=loop-vectorize` and `-Rpass-missed=loop-vectorize` to confirm whether the pragma had an effect.

```cpp
#include <omp.h>

void saxpy(int N, const float *x, const float *y, float *z, float a) {

  #pragma clang loop vectorize(enable)

  }
}
```

In this snippet:  
1. **OpenMP** splits the index range `[0, N)` across threads.  
2. **Clang’s loop vectorizer** then processes each thread’s chunk, emitting SIMD instructions for the inner loop.

<hr>

## 🔄 Ordering and Interactions

- Place `#pragma omp parallel for` (or any OpenMP work-sharing pragma) **directly above** the loop.  
- Immediately after, insert `#pragma clang loop vectorize(enable)`.  
- The OpenMP pragma directs thread-level scheduling; the Clang pragma influences only per-thread SIMD.

<hr>

## ✨ Variants of “#pragma omp atomic”

<b>OpenMP’s atomic directive</b> supports four primary forms plus optional memory‐ordering clauses. The variants are:  
- **read**  
- **write**  
- **update**  
- **capture**  

Each tells the compiler what kind of atomic access you’re performing, so it can generate the appropriate hardware instructions or locks.

<hr>

### 🔍 1. read

Use when you want to **atomically load** a shared scalar into a local variable.

```cpp
int shared = 0, local;
#pragma omp atomic read
local = shared;
```

<hr>

### 🔍 2. write

Use when you want to **atomically store** a local value into a shared scalar.

```cpp
int shared = 0, local = 5;
#pragma omp atomic write
shared = local;
```

<hr>

### 🔍 3. update

Use when you want to **atomically read-modify-write** with a single operator. Common with `+=`, `*=`, etc.

```cpp
int counter = 0;
// Atomically increment counter
#pragma omp atomic update
counter += 1;
```

<hr>

### 🔍 4. capture

Use when you need both the **old** and **new** value of a shared scalar in one atomic step.

```cpp
int shared = 0, old_val, new_val;
// Atomically capture shared before and after increment
#pragma omp atomic capture
{
  old_val = shared;
  new_val = shared + 1;
  shared = new_val;
}
```

<hr>

## ⚙️ Memory‐Ordering Clauses

Since OpenMP 4.5 you can specify a memory‐ordering constraint to control visibility across threads. Append one of:  
- **seq_cst** (default): Sequential consistency.  
- **acq_rel**: Acquire/release semantics.  
- **acquire**: Ensure subsequent loads see up‐to‐date values.  
- **release**: Ensure preceding stores complete before the atomic.  

### 🚀 Example with Memory‐Order

```cpp
int x = 0;
// atomic store with release semantics
#pragma omp atomic write release
x = 42;

// atomic load with acquire semantics
int y;
#pragma omp atomic read acquire
y = x;
```

<hr>

Using the appropriate variant and memory‐ordering clause ensures minimal synchronization overhead while preserving correctness in concurrent regions.

## When to Use Each

<b>#pragma omp for</b>  
Use when your goal is to split a large loop across multiple threads. It does not guarantee any vectorization; it simply hands out different index ranges to each thread.

<b>#pragma omp simd</b>  
Use when you want to force or encourage the compiler to generate SIMD instructions for the loop body within each thread. It does not spawn threads.

<hr>

## Can They Be Combined?

<b>Yes.</b> You can combine them to exploit both thread-level and data-level parallelism. The most common pattern is:

```cpp
#pragma omp parallel for simd
for (int i = 0; i < N; ++i) {
    C[i] = A[i] + B[i];
}
```

This single pragma does three things:  
1. **parallel**: creates a team of threads.  
2. **for**: divides the iteration space among threads.  
3. **simd**: inside each thread’s assigned chunk, vectorizes the loop.

<hr>

## 🚀 Can “#pragma omp simd” Apply to Non-Loop Blocks?

<b>No.</b> The OpenMP `simd` directive is explicitly designed to apply to loop constructs (`for`, `do`, or `while` loops). You cannot attach `#pragma omp simd` to an arbitrary block of code or multiple lines of statements outside of a loop.

<hr>

## 🔍 Why It’s Loop-Only

OpenMP’s SIMD model works by mapping successive loop iterations to vector lanes. Without a loop, there is no iteration space to divide into SIMD lanes, so the directive has no defined semantics.

<hr>

## 🛠️ What You Can Do Instead

### 1. Encapsulate Work into a Loop  
If you have a fixed number of operations, wrap them in a small loop:

```cpp
float tmp[4] = {a, b, c, d};
#pragma omp simd
for (int i = 0; i < 4; ++i) {
    tmp[i] = some_op(tmp[i]);
}
```

### 2. Use Compiler Vector Extensions  
For straight-line code, you can leverage Clang or GCC vector extensions:

```cpp
typedef float v4f __attribute__((vector_size(16)));
v4f v = {a, b, c, d};
v = some_intrinsic_op(v);
a = v[0]; b = v[1]; // …
```

### 3. Employ Intrinsics Directly  
Use `<immintrin.h>` intrinsics for manual SIMD on blocks:

```cpp
#include <immintrin.h>
__m128 v = _mm_set_ps(a, b, c, d);

// Store back
_mm_store_ps(&a, v);
```

<hr>

Although `#pragma omp simd` cannot decorate arbitrary code blocks, wrapping operations in a minimal loop or using compiler/intrinsic facilities lets you achieve SIMD for multi-statement sequences.

## When “More Optimal” Means “Platform-Specific”  

If you’re willing to drop pure‐C portability and write a tiny bit of inline assembly (or compiler-builtin), you can squeeze out every last cycle:

```cpp
static inline __attribute__((always_inline, hot))
__float128 fmaxq(__float128 a, __float128 b) {
    // compare a and b, then conditionally move b→a if a < b
    asm volatile(
      "ucomiq %1, %0\n\t"        // unordered compare a vs b
      "cmovbq %1, %0"            // if CF=1 or PF=1 (a < b or unordered), a←b
      : "+x"(a)                  // a is both input and output
      : "x"(b)
      : "cc"                     // clobbers flags
    );
    return a;
}
```

• `ucomiq` tests a vs b (handles NaN as “unordered”).  
• `cmovbq` moves b into a if the “below” flag (CF) or “unordered” (PF) is set.  

This is exactly what the C-level ternary emits under `-O3` on Clang/GCC, but written out in asm you know precisely which op-codes you get.

1) **Compiler built-in**  
   ```cpp
   static inline __attribute__((always_inline, hot))
   __float128 fmaxq(__float128 a, __float128 b) {

   }
   ```  
   This maps to the same CMP+CMOV under the hood, but also gives you well-defined NaN handling per IEEE.

2) **Branchless bit-mask** (pure C, but more verbose):

   ```cpp
   __float128 fmaxq(__float128 a, __float128 b) {
     bool gt = a > b;                     // compile to a cmov + test
     __uint128_t mask = -(__uint128_t)gt; // all-ones if gt, zero otherwise
     __uint128_t ai = *(__uint128_t*)&a;
     __uint128_t bi = *(__uint128_t*)&b;
     return *(__float128*)&((ai & mask) | (bi & ~mask));
   ```  

   This too ends up as CMOV in practice, but shows the mask trick.

```cpp
__float128 frexpq(__float128 x, int *eptr) {
    // Handle zero, NaN, and ±∞ quickly
    if (__builtin_isnan(x) || __builtin_isinf(x) || x == 0) {
        *eptr = 0;
        return x + x;
    }

    // Extract raw bits
    uint64_t hi, lo;

    int exp = int((hi >> 48) & 0x7FFF);

        constexpr __float128 two114 = (__float128)0x1.0p114Q;
        x *= two114;
        GET_FLT128_WORDS64(hi, lo, x);
        exp = int((hi >> 48) & 0x7FFF);
        exp -= 114;
    }

    // Compute final exponent and assemble mantissa in [0.5,1)
    *eptr = exp - 0x3FFF + 1;
    // Clear exponent bits and set bias (0x3FFE)
    hi = (hi & 0x8000FFFFFFFFFFFFULL) | (uint64_t(0x3FFE) << 48);
    SET_FLT128_WORDS64(hi, lo, x);
    return x;
```

If you prefer a header-only, branch-reduced version without pulling in quadmath, here’s a streamlined bit-twiddling variant:

```cpp
static inline __attribute__((always_inline, hot))
__float128 roundq(__float128 x) {
    uint64_t hi, lo;
    GET_FLT128_WORDS64(hi, lo, x);

    // Extract unbiased exponent j0 = exp - bias
    int j0 = int((hi >> 48) & 0x7FFF) - 0x3FFF;

    // |x| < 0.5 → round toward ±0 to zero
    if (j0 < 0) {
        hi &= 0x8000'0000'0000'0000ULL;         // keep sign
        hi |= 0x3FFF'0000'0000'0000ULL;         // produce ±0.0…5
        lo  = 0;
    }
    // |x| >= 2^112 or NaN/Inf → return x + x to preserve NaN
    else if (j0 > 111) {
        return ((uint16_t)(hi >> 48) == 0x7FFF)
               ? x + x
               : x;
    }
    else {
        // Mask for fractional bits in high and low words
        uint64_t frac_hi = (0x0000'FFFF'FFFF'FFFFULL >> j0);
        uint64_t frac_lo = (j0 < 64) 
            ? ~0ULL >> (j0 + 16) 
            : 0xFFFF'FFFF'FFFF'FFFFULL;

        // If already integral, exit early
        if (((hi & frac_hi) | (lo & frac_lo)) == 0)
            return x;

        // Add 0.5 ulp at the rounding position
        if (j0 < 64) {
            lo += (1ULL << (63 - j0));
            if (lo < (1ULL << (63 - j0))) {
                hi += 1;  // carry
            }
        } else {
            hi += (1ULL << (112 - j0));
        }

        // Clear fractional bits
        hi &= ~frac_hi;
        lo &= ~frac_lo;
    }

    SET_FLT128_WORDS64(x, hi, lo);
    return x;
}
```

### ✨ Key Improvements

- **Reduced Branches:** Consolidates normal, subnormal, and large-exponent cases into three clear paths.  
- **Single-Shot Masks:** Precomputes masks for both high and low words to test and clear fractional bits.  
- **Carry Handling:** Adds the 0.5-ulp with proper carry into the high 64 bits.  
- **Early-Exit Integral Check:** Detects already integral values with one combined mask test.

This version compiles down to a handful of integer ops and very few unpredictable branches, matching or beating the original in hot-path performance while preserving full IEEE-128 rounding semantics.

```cpp
__float128 scalbnq(__float128 x, int n) {
    uint64_t hi, lo;
    GET_FLT128_WORDS64(hi, lo, x);

    // Extract sign, exponent, and mantissa mask
    uint64_t sign = hi & UINT64_C(0x8000000000000000);
    int      exp  = int((hi >> 48) & 0x7FFF);
    const int  BIAS = 0x3FFF;

    // Handle zero, NaN, Inf
    if (exp == 0) {
        // Zero or subnormal: scale x by 2^114 to normalize, adjust exponent
        if ((lo | (hi & UINT64_C(0x7FFFFFFFFFFF'FFFF))) == 0)
            return x;  // zero
        constexpr __float128 two114 = (__float128)0x1.0p114Q;
        x *= two114;
        GET_FLT128_WORDS64(hi, lo, x);
        exp = int((hi >> 48) & 0x7FFF) - 114;
    }
    else if (exp == 0x7FFF) {
        // NaN or Inf
        return x + x;
    }

    // Compute new exponent and check overflow/underflow bounds
    int newe = exp + n;
    if (newe > 0x7FFE) {
        // overflow
        constexpr __float128 huge = (__float128)1.0e+4900Q;
        return copysignq(huge, x);
    }
    if (newe <= 0) {
        // underflow to subnormal or zero
        if (newe <= -114) {
            constexpr __float128 tiny = (__float128)1.0e-4900Q;
            return copysignq(tiny, x);
        }
        // extract subnormal: shift into mantissa
        hi = sign | 0;        // zero out exponent, mantissa
        lo = 0;
        SET_FLT128_WORDS64(x, hi, lo);
        constexpr __float128 twom114 = (__float128)0x1.0p-114Q;
        return x * twom114 * __builtin_powi((__float128)2.0Q, newe + 114);

    // Normal range: just reassemble sign | new exponent | mantissa
    hi = sign | (uint64_t(newe) << 48) | (hi & UINT64_C(0x0000FFFFFFFF'FFFF));
    SET_FLT128_WORDS64(x, hi, lo);
    return x;
}
```

• **Direct Exponent Arithmetic:** Computes `newe = exp + n` once, then dispatches overflow, underflow, or normal paths.  
• **Minimal Branches:** Only three main branches (special, underflow, overflow), reducing pipeline stalls.
